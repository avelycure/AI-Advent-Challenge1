# Терминальный чат с LLM

CLI-клиент к восьми провайдерам — **DeepSeek**, **ChatGPT (OpenAI)**, **YandexGPT**,
**GigaChat**, **Grok (xAI)**, **OpenRouter**, **Groq** и **Google Gemini**.
Отправляет запрос в LLM через API, получает ответ и показывает его в терминале.

Через OpenRouter и Groq доступны модели **без оплаты и без привязки карты**.

Диалог живёт долго: вся переписка — и реплики пользователя, и ответы модели —
уходит в LLM при каждом запросе, поэтому модель помнит контекст разговора.

## GitHub MCP

Агент умеет подключать инструменты отдельного MCP-сервера. Пример для
статистики GitHub находится в соседнем проекте `AI-Advent-MCP/mcp1`.

Сначала настройте токен по инструкции `AI-Advent-MCP/mcp1/README.md` и
запустите сервер в первом терминале:

```bash
cd ../AI-Advent-MCP/mcp1
npm install
npm run server
```

Во втором терминале подготовьте окружение агента и проверьте полный цикл без
платного LLM:

```bash
cd ../../AI-Advent-Challenge1
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python mcp_demo.py
```

Или дать настоящий инструмент настроенному агенту:

```bash
./agent --config examples/github-mcp.yaml \
  --ask "Собери статистику GitHub и назови число репозиториев и звёзд" --json
```

URL сервера по умолчанию — `http://127.0.0.1:3000/mcp`. Его можно изменить
через `MCP_URL`, а путь к Node-клиенту — через `MCP_CLIENT_SCRIPT`.

В интерактивном режиме команда `/mcp` показывает доступность сервера и список
инструментов. Если сервер был недоступен при запуске, уже настроенные инструменты
заработают после его восстановления; чтобы подключить новые инструменты из
обновившегося каталога, перезапустите агент.

Конфигурация примера запрашивает статистику всех доступных репозиториев. При
работе с внешней LLM агрегаты приватных репозиториев и обезличенные метрики
top-N отправляются провайдеру модели. Для публичной статистики передавайте
инструменту `visibility: "public"`.

## Быстрый старт

```bash
./run.sh
```

Скрипт сам создаёт виртуальное окружение, ставит зависимости и запускает чат.
Нужен Python 3.8 или новее (проверено на системном Python 3.9 из macOS).

Если хочется без скрипта:

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python chat.py
```

### Посмотреть, ничего не подключая

```bash
./run.sh --demo
```

Ответы формирует локальная заглушка, запросы в сеть не уходят, токены не тратятся.
Реквизиты в этом режиме можно вводить любые. Удобно, чтобы увидеть интерфейс
и поведение счётчиков до того, как заводить ключи.

## Что происходит при запуске

Программа проведёт по шагам:

1. **Выбор LLM** — список из восьми провайдеров с моделями и тем, что нужно для доступа.
2. **Дополнительный реквизит** — только для YandexGPT, у которого кроме ключа нужен
   идентификатор каталога.
3. **Ключ** — со ссылкой на страницу, где его выдают. Ввод скрыт, ключ никуда
   не сохраняется. Если в окружении есть переменная с ключом, программа предложит
   взять его оттуда.
4. **Проверка доступа** — до начала диалога, чтобы не узнать о неверном ключе
   на первом же сообщении. При ошибке ключ можно ввести заново.
5. **Выбор модели** — из моделей выбранного провайдера.

Дальше открывается диалог.

### Чтобы не вводить реквизиты каждый раз

Программа сама подхватывает уже сохранённые значения и предлагает их одним
нажатием Enter. Порядок поиска: переменная окружения, затем локальный файл,
и только потом ручной ввод.

| Провайдер | Переменная окружения | Файл |
|---|---|---|
| DeepSeek | `DEEPSEEK_API_KEY` | `~/.deepseek-key` |
| ChatGPT (OpenAI) | `OPENAI_API_KEY` | `~/.openai-key` |
| YandexGPT | `YANDEX_API_KEY` | `~/.yandex-key` и `~/.yandex-folder` |
| GigaChat | `GIGACHAT_CREDENTIALS` | `~/.gigachat-key` |
| Grok (xAI) | `XAI_API_KEY` | `~/.grok-key` |
| OpenRouter | `OPENROUTER_API_KEY` | `~/.openrouter-key` |
| Groq | `GROQ_API_KEY` | `~/.groq-key` |
| Google Gemini | `GEMINI_API_KEY` | `~/.gemini-key` |

Дополнительно просматривается каталог `~/.config/llm-chat/` — например,
`~/.config/llm-chat/gigachat.key`.

Файл создаётся одной командой:

```bash
echo 'ваш-ключ' > ~/.gigachat-key && chmod 600 ~/.gigachat-key
```

Пустые строки и строки, начинающиеся с решётки, пропускаются — файл можно
снабдить комментарием. Если найдено сразу несколько источников, программа
покажет список и даст выбрать, включая пункт «ввести вручную». Если у файла
права позволяют читать его посторонним, появится предупреждение с командой
исправления.

Ключи программа только читает и никогда не записывает. Чтобы принудительно
спросить реквизиты заново, запустите с флагом `--ask-keys`.

### Grok (xAI)

Ключ берётся в консоли `console.x.ai`, раздел API Keys, и начинается с `xai-`.
Протокол OpenAI-совместимый, адрес `https://api.x.ai/v1`.

**Бесплатного тарифа у xAI нет.** Без купленных кредитов API отвечает отказом
на любой запрос, включая список моделей:

```
403 permission-denied: Your newly created team doesn't have any credits
    or licenses yet.
```

Программа переводит это в понятное сообщение и предлагает выбрать другого
провайдера. Отдельно стоит знать, что на неверный ключ xAI отвечает кодом 400,
а не 401, как остальные, — этот случай тоже разобран отдельно.

Набор моделей зависит от аккаунта: у ключа есть свой список прав. Посмотреть
его можно в консоли или запросом к `https://api.x.ai/v1/api-key` — он работает
даже без кредитов и заодно проверяет, что ключ действителен.
### OpenRouter — бесплатные модели

Один ключ открывает модели разных разработчиков. В программу вынесены три
бесплатные. Бесплатность не заявлена на слово: в открытом каталоге
`openrouter.ai/api/v1/models` у них нулевая цена и за ввод, и за вывод.

| Модель | Окно | Чем хороша |
|---|---|---|
| `nex-agi/nex-n2.5-pro:free` | 262 144 | отвечает коротко и по существу |
| `nvidia/nemotron-3.5-lightning:free` | 1 000 000 | самое большое окно; рассуждает перед ответом |
| `liquid/lfm-2.5-2.6b:free` | 65 536 | самое **маленькое** окно — на нём видно переполнение |

Ключ берётся на `openrouter.ai/keys`, начинается с `sk-or-v1-`, карта не нужна.

**Каталог провайдера меняется.** Прежние `minimax/minimax-m3:free` и
`z-ai/glm-5.2:free` из него пропали и отвечают кодом 404 — все три нынешние
проверены живым запросом. Если модель вдруг перестала отвечать, сверьтесь
с `openrouter.ai/api/v1/models`: скорее всего её убрали.

**LFM 2.5 — единственная модель, на которой можно увидеть отказ самого
провайдера.** У остальных окно так велико, что переполнить его вручную не
выйдет: не хватит ни вставки, ни разговора. На запрос шире 65 536 токенов она
отвечает `This endpoint's maximum context length is 65536 tokens`, и агент
переводит это в «Контекст переполнен». Как это показать — в разделе
[Что ломается при переполнении](#что-ломается-при-переполнении).

Особенность бесплатного тарифа: модели делят общую очередь и временами
отвечают отказом «перегружена». Это не про ваш ключ и не про баланс —
программа так и говорит и предлагает выбрать другую модель. Nemotron и LFM
рассуждают перед ответом: на короткий вопрос у них уходит около сотни токенов
выхода, и с маленьким `max_tokens` текста не будет вовсе — весь лимит съест
рассуждение.

### Groq — бесплатный тариф

Ключ берётся на `console.groq.com/keys`, начинается с `gsk_`, карта не нужна.
В программу вынесены шесть моделей: **Qwen 3.8 27B** и **Qwen 3.6 27B**,
**GPT-OSS 120B** и **GPT-OSS 20B**, а также системы **Compound** и
**Compound Mini** — модели с веб-поиском и запуском кода.

Размеры окон взяты не из документации, а из ответа самого `/v1/models`:
у Qwen 3.8 там 131 042 токена, а не круглые 131 072. Llama 3.1 и 3.3, которые
описаны в документации, обычному ключу не выдаются — Groq перевёл их
в тариф Enterprise.

Лимиты бесплатного тарифа программа не угадывает, они приходят в заголовках
ответа: **1000 запросов в сутки** и **8000 токенов в минуту** на запрос и ответ
вместе, плюс отдельный потолок в **1000 токенов вывода в минуту**. Практическое
следствие: длинный диалог упрётся в минутный лимит заметно раньше, чем
в размер окна.

Главная особенность — все модели Groq **рассуждают перед ответом, и рассуждение
тратит тот же `max_tokens`, что и сам ответ**. Если этого не учесть, короткий
запрос возвращает пустой текст: весь лимит ушёл на размышление. Программа
задаёт каждой модели свой режим, потому что единого не существует: Qwen
позволяет отключить рассуждение совсем (`reasoning_effort: none`), GPT-OSS
принимает только `low`, `medium` и `high`, а системы Compound не принимают это
поле вовсе. Поля, которые модель не приняла, клиент убирает и повторяет запрос.

### Google Gemini

Ключ берётся в Google AI Studio, начинается с `AIza`. Работает через
OpenAI-совместимый слой `generativelanguage.googleapis.com/v1beta/openai/`.
У Google есть бесплатный тариф с ограничением по числу запросов в сутки,
карта не нужна.

Особенность: списка моделей по OpenAI-совместимому пути нет, поэтому проверка
ключа откладывается до первого запроса. На неверный ключ Google отвечает кодом
400, а не 401, — этот случай разобран отдельно.

### DeepSeek и ChatGPT

Заводится ключ в личном кабинете, копируется целиком (строка начинается с `sk-`).
Оба сервиса платные, бесплатного тарифа нет — при нулевом балансе запрос вернёт
отказ, а не ответ.

В программу вынесены пять моделей ChatGPT текущего поколения: **GPT-5.4 mini**
и **GPT-5.4 nano** (окно 400 000, вход до 272 000), **GPT-5.4**, **GPT-5.5**
и **GPT-6 Astra** (окно 1 050 000). Предел ответа у всех пяти — 128 000 токенов.

Три особенности, которые стоит знать заранее.

**GPT-5.5 и GPT-6 Astra не принимают `temperature`** — только значение по
умолчанию. Программа это переживает: параметр убирается из запроса, и появляется
панель о том, что он не подействовал. Но задать случайность на этих моделях
нельзя, и сравнивать их с остальными по температуре бессмысленно.

**Размеры окон взяты из документации, а не из API.** У Groq они приходят прямо
в `/v1/models`, у OpenAI ответ содержит только `id`, `created`, `owned_by`
и `shutdown_date`. Проверить окно запросом тоже не выйдет: тарифный лимит
организации срабатывает раньше, чем лимит модели.

**Тариф ограничивает запрос сильнее модели.** Лимит в токенах в минуту у
обычной организации — 200 000, поэтому окно на миллион в одном запросе не
заполнить. И отдельно: у GPT-5.4 вход длиннее 272 000 токенов тарифицируется
по двойной цене за вход и полуторной за выход — на всю сессию, а не только
за длинный запрос.

### YandexGPT

Реквизита два, и это главное отличие от остальных.

**Идентификатор каталога** виден в адресной строке консоли Yandex Cloud
(`console.yandex.cloud/folders/b1g…`) или на странице каталога в поле
«Идентификатор». Начинается с `b1g`.

**API-ключ** выдаётся не аккаунту, а *сервисному аккаунту*. Нужно создать сервисный
аккаунт в каталоге, выдать ему роль `ai.languageModels.user`, затем в его карточке
выбрать «Создать новый ключ» → «Создать API-ключ». Строка показывается один раз
и начинается с `AQVN`.

Каталог нужен потому, что модель у Яндекса задаётся не именем, а адресом вида
`gpt://<идентификатор_каталога>/yandexgpt-lite/latest`. Программа собирает этот
адрес сама.

### GigaChat

В личном кабинете `developers.sber.ru/studio` создаётся проект GigaChat API,
затем «Создать новый» выдаёт **ключ авторизации** — длинную строку Base64.
Её показывают один раз.

Дальше программа всё делает сама: меняет ключ авторизации на access-токен запросом
к серверу авторизации Сбера, кэширует токен и обновляет его до истечения.

У GigaChat есть бесплатный лимит для физических лиц — на момент проверки это были
250 млн токенов на GigaChat 2 Lite и меньшие объёмы на старших моделях. Актуальные
цифры смотрите в личном кабинете, они менялись.

**Сертификат.** Сервер Сбера использует сертификат НУЦ Минцифры, которого нет
в стандартном хранилище. Если появится ошибка проверки сертификата:

```bash
curl -k "https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt" >> $(python -m certifi)
```

## Что видно на экране

**Вверху — тема диалога.** Её формулирует сама LLM после первого ответа отдельным
коротким запросом и обновляет каждые пять обменов, если разговор ушёл в сторону.
Справа в той же строке — выбранные провайдер и модель.

**В середине — переписка.** Ответы модели отрисовываются с разметкой Markdown:
списки, заголовки, блоки кода. Программа подгоняет кадр под высоту терминала:
если сообщения не помещаются, старые сворачиваются, а сверху появляется строка
«↑ выше ещё N сообщений». Вся переписка при этом сохраняется — её показывает `/history`.

**Внизу — счётчики:**

- полоса и процент заполнения контекстного окна модели;
- сколько токенов занято и каков размер окна;
- резерв под ответ — место, которое всегда оставляется модели на ответ;
- сколько токенов свободно;
- **до конца диалога** — на сколько ещё сообщений хватит места; оценка считается
  по среднему размеру обмена в этом конкретном разговоре;
- сколько токенов потрачено за сессию и сколько было запросов к API.

**Во время ожидания** крутится спиннер с именем модели.

Когда контекст подходит к концу, появляется предупреждение, а сообщение, которое
уже не помещается в окно, программа не отправит — предложит начать новый диалог.

## Команды

| Команда | Действие |
|---|---|
| `/help` | справка по командам |
| `/history` | показать всю переписку целиком |
| `/stats` | подробная статистика по токенам |
| `/tokens` | из чего сложится следующий запрос и как росла цена диалога |
| `/strategy` | как собирается запрос: `full`, `window`, `facts`, `summary` |
| `/facts` | картотека важных сведений разговора; её можно поправить руками |
| `/memory` | три явных слоя памяти: диалог, текущая задача, профиль и проект |
| `/profile` | персональные настройки ответов и правила для типов задач |
| `/task` | показать этап, шаг и контрольные ворота жизненного цикла |
| `/pause`, `/resume` | пауза и продолжение с сохранённого места |
| `/checkpoint` | запомнить место разговора, от которого отводят ветки |
| `/branch` | отвести ветку и продолжать разговор в ней |
| `/branches` | список веток и точек возврата |
| `/switch` | перейти в другую ветку разговора |
| `/summary` | пересказ, которым заменено начало разговора |
| `/compress` | свернуть начало разговора в пересказ прямо сейчас |
| `/config` | конфиг агента целиком — его можно сохранить и запустить с `--config` |
| `/mcp` | подключённые MCP-серверы, их статус и доступные инструменты |
| `/agent` | вызвать под-агента с нужным конфигом; без аргументов — список конфигов |
| `/change_llm_params` | показать или изменить параметры генерации |
| `/reset_llm_params` | вернуть параметры к значениям по умолчанию |
| `/change_model` | сменить модель или провайдера; без аргументов — список с номерами |
| `/retry` | переспросить последний вопрос на текущей модели |
| `/new` | начать новую сессию: история и счёт обнуляются, прежняя остаётся на диске |
| `/exit` | выход |

### Контролируемые переходы задачи

Задача проходит только цепочку `planning → execution → validation → done`.
Реализация не начинается до явного утверждения плана, а `done` недоступен без
успешной проверки и записи её результата. Фразу `Утверждаю план` можно написать
обычным сообщением; для ручной коррекции доступны `/task approve`, `/task next`
и `/task validate результат проверки`. Запрещённый переход не применяется:
ассистент объясняет причину и остаётся на прежнем этапе.

Пауза и сохранение сессии удерживают не только этап и шаг, но также утверждение
плана и результат проверки. Подробнее: [docs/feature-task-state-machine.md](docs/feature-task-state-machine.md).

### Один вопрос на разных моделях

Модель меняется прямо в диалоге, история при этом остаётся на месте. Типичный
прогон выглядит так: задать вопрос, `/change_model 4`, `/retry` — и в переписке
рядом стоят два ответа на один вопрос, каждый подписан своей моделью.

`/retry` отправляет историю **по этот вопрос включительно**: прежние ответы на
него в запрос не идут, поэтому новой модели достаётся ровно та же задача, а не
задача «посмотри, что ответил предыдущий». В переписке видны все ответы, но в
следующий обычный запрос уходит только последний из них.

Ключ каждого провайдера спрашивается один раз за запуск: возврат к уже
опробованному провайдеру ничего не спрашивает. В списке моделей это видно
по столбцу «Ключ» — `готов` или `спросит`.

### Время, токены и стоимость

Под каждым ответом подписано, чего он стоил: время запроса, вход и выход
в токенах, отдельно — скрытое размышление, если модель его показала, и цена.
В нижней строке та же цена накапливается за всю сессию, подробности — в `/stats`.

```
╰──────────────────── 12.5 с · 361 → 8 000 ток. · размышление 7 990 · $0.4036 ─╯
```

Это и делает сравнение моделей осмысленным: после `/change_model` и `/retry`
два ответа на один вопрос стоят рядом, и видно не только что они разные,
но и во сколько обошёлся каждый.

Четыре оговорки, чтобы числам можно было верить.

**Цены взяты из официальных прайсов провайдеров** и записаны за миллион
токенов:

| Провайдер | Модели | Вход | Выход |
|---|---|---|---|
| ChatGPT | gpt-5.4-nano · mini · gpt-5.4 · 5.5 · gpt-6-astra | $0.20 … $10.00 | $1.25 … $50.00 |
| Grok | grok-4.3 · 4.5 · 4.6 | $1.25 … $2.00 | $2.50 … $6.00 |
| Gemini | 2.5-flash · 3.5-flash · 3.7-flash | $0.30 … $1.50 | $2.50 … $9.00 |
| YandexGPT | Lite · Pro | ₽200 · ₽800 | ₽200 · ₽800 |
| GigaChat | 2 Lite · Pro · Max | ₽65 · ₽500 · ₽650 | столько же |
| OpenRouter, Groq | все | бесплатный тариф | бесплатный тариф |
| DeepSeek | v4-flash · v4-pro | $0.44 · $1.32 | $1.32 · $3.96 |

**Рубли и доллары не складываются.** У каждой модели своя валюта прайса, и
итог по сессии считается по каждой отдельно: после переключения с ChatGPT на
YandexGPT в нижней строке будет `₽0.40 + $0.0014`.

**У DeepSeek прайс двойной.** Цена в таблице записана по дорогому тарифу:
в часы наименьшей нагрузки она вдвое ниже. Считать по дешёвому нельзя — тогда
обещанный потолок трат не держался бы. Вход, зачтённый по кешу, стоит ещё
в тридцать раз меньше: $0.014 за миллион у Flash.

**Прежнее имя `deepseek-chat` оставлено, но без цены.** В каталоге провайдера
его больше нет, хотя запросы он пока принимает. На какую из моделей V4 оно
переводится — не сказано, поэтому программа показывает прочерк, а итог сессии
помечает знаком `≥`, чтобы неполная сумма не выглядела полной. Имя
`deepseek-reasoner` пропало совсем.

**Часть цен — с оговорками**, они видны в `/stats` строкой «Оговорка к цене»:
у Grok тариф удваивается при промпте от 200 000 токенов, у Gemini 3.7 Flash
нынешняя цена действует до 31 декабря 2026 года, у GigaChat поштучного прайса
нет вовсе — цена выведена из стоимости пакета. Рублёвые цены включают НДС.

**Размышление уже входит в выход.** Строка «размышление» — не добавка к
полученным токенам, а их часть: провайдер тарифицирует её как обычный выход.
Показана отдельно потому, что иначе непонятно, за что заплачено: ответ
в пять символов может стоить как страница текста.

**Время включает повторы.** Если провайдер отверг параметр и запрос был
переписан и отправлен снова, в замер войдут обе попытки — столько запрос
и правда занял. Первый запрос к провайдеру медленнее из-за установки
соединения, так что для честного замера скорости его лучше отбросить.

**Длинный контекст считается по обычной цене.** У GPT-5.4 и GPT-5.5 вход
длиннее 272 000 токенов стоит вдвое дороже, но тарифный лимит организации
(обычно 200 000 токенов в минуту) не даёт отправить такой запрос, поэтому
второй тариф в расчёт не заложен.

### Куда уходят токены — `/tokens`

`/stats` отвечает на вопрос «сколько потрачено». `/tokens` отвечает на три
других: **из чего** сложится следующий запрос, **можно ли верить** этим числам
и **как дорожал** разговор.

```
 Часть                     Токенов   Доля
 Системный промпт               83    33%
 История диалога               152    60%
 Новый вопрос                   15     6%
 Служебная разметка              3     1%
 Итого по частям               253
 Поправка на токенизатор     ×0.64
 Итого вход                    161
 Резерв под ответ              500
 Займёт от окна                661    33%
```

**Платят за всю переписку, а не за вопрос.** Каждый следующий запрос отправляет
историю целиком, поэтому десятый вопрос дороже первого, хотя набран теми же
словами. Таблица «Рост по обменам» показывает это по шагам: вход, выход, всего
и цену — за шаг и накопленным итогом.

**Оценка неотправленного врёт, и видно, насколько.** Локально размер считает
токенизатор ChatGPT (`tiktoken/cl100k_base`), а отвечает Qwen, GLM или
YandexGPT со своим. На живом прогоне Groq/Qwen на русском тексте локальная
оценка оказалась завышена на 36–55%. Провайдер называет точное число с каждым
ответом — из него выводится поправка, и следующая оценка умножается на неё.
Поэтому в таблице стоят обе цифры: своя сумма по частям и итог после поправки.

**Что не так с одной цифрой «занято 4 812».** По ней непонятно, что сокращать.
Раскладка по частям отвечает сразу: системный промпт правят один раз, историю
сбрасывают, вопрос укорачивают.

### Что ломается при переполнении

Три беды выглядят похоже, а лечатся по-разному, и программа их различает.

| Что случилось | Как видно | Что делать |
|---|---|---|
| ответ упёрся в `max_tokens` | «Ответ обрезан», `finish_reason = length` | поднять `max_tokens`; место в окне ещё есть |
| диалог не влезает в окно | отказ с числами: сколько лишних токенов | `/new`, короче вопрос или `on_overflow=trim` |
| кончились деньги или лимит запросов | «исчерпан лимит» | поднять `budget` |

Переполнение ловит сам агент, а не интерфейс: этим путём ходят и под-агент,
и `--json`, и скрипты сравнения. Отказ выглядит так:

```
диалог не помещается в окно модели: 905 токенов истории и вопроса
плюс 300 резерва под ответ — это 1205 при окне 1200, лишних 5
```

Ответа на этот вопрос нет, вопрос из истории убирается, деньги за него не
потрачены.

Когда отвечает сам провайдер — с `on_overflow=send` или когда наша оценка
промахнулась, — его слова показываются следом за советом. Свои числа он
считает своим токенизатором, и они точнее нашей оценки:

```
Контекст переполнен: диалог не помещается в окно модели.
Начните новый диалог командой /new или задайте вопрос короче.
Провайдер: This endpoint's maximum context length is 65536 tokens.
However, you requested about 145187 tokens (141091 of text input,
4096 in the output).
```

**Можно отдать слово провайдеру.** `--set history.on_overflow=send` отключает
свою проверку и отправляет заведомо не помещающийся запрос. Нужно ровно затем,
чтобы увидеть отказ самого провайдера — иначе до него очередь не доходит.
Программа предупредит, на сколько токенов запрос вылезает, и покажет ответ
как есть.

**Можно не падать, а забывать начало.** `--set history.on_overflow=trim`
выбрасывает самые старые обмены «вопрос — ответ», пока запрос не влезет.
Системный промпт и сам вопрос не трогаются никогда. Диалог продолжается —
но модель теряет память: на живом прогоне после обрезки на вопрос «как меня
зовут» она ответила «Неизвестно», хотя имя было названо первым сообщением.
Программа об этом говорит прямо, а не молча.

**Окно можно сузить.** `--set history.window=2000` загоняет агента в окно
меньше модельного. Нужно, чтобы увидеть переполнение, не набивая сто тысяч
токенов: на бесплатном тарифе раньше упрёшься в его собственный лимит.
Резерв под ответ при этом ужимается до четверти окна, а заданный вручную
`max_tokens` больше окна отвергается при запуске.

### Три диалога рядом — `./tokens.sh`

```bash
./tokens.sh                                    на заглушке, бесплатно
./tokens.sh --live --provider groq             настоящие запросы
./tokens.sh --window 2000 --step               своё окно, по шагам
```

Одни и те же вопросы задаются четыре раза: коротким диалогом, длинным, до
отказа и до отказа с обрезкой. В конце — таблица сравнения и выводы, посчитанные
по этим же числам, а не написанные заранее.

| Прогон | Обменов | Вход | Выход | Всего | Чем кончился |
|---|---|---|---|---|---|
| Короткий | 3 | 906 | 376 | 1 282 | дошёл |
| Длинный | 9 | 7 102 | 1 135 | 8 237 | дошёл |
| Сверх лимита | 23 | 44 153 | 2 933 | 47 086 | отказ |
| С обрезкой | 30 | 69 101 | 3 781 | 72 882 | обрезка |

Видно и то, о чём обычно не думают: обрезка обходится **дороже** отказа —
разговор просто продолжается дольше, и каждый его круг снова оплачивается
целиком.

## Явная память: три слоя

Не каждое «запомни» должно означать одно и то же. Агент разделяет память по
сроку жизни и ничего сам не переносит из одного слоя в другой:

| Слой | Что в нём | Как попадает | Когда исчезает |
|---|---|---|---|
| `short` | реплики текущего диалога | любая обычная реплика | при `/new`; у каждой ветки своя копия |
| `working` | цель, ограничения, промежуточные данные и открытые вопросы текущей задачи | только `/memory working ключ=значение` | при `/new`; сохраняется с сессией и ветвится вместе с задачей |
| `long` | профиль пользователя, правила, решения и знания проекта | только `/memory long раздел ключ=значение` | не исчезает при `/new` и доступен в следующих сессиях |

Посмотреть все три слоя:

```text
Вы › /memory
```

Краткосрочная память заполняется самим разговором, вручную писать в неё нельзя.
Для двух остальных слоёв место назначения называется прямо в команде:

```text
Вы › /memory short
Вы › /memory working цель=подготовить релиз
Вы › /memory working срок=к 1 марта
Вы › /memory long profile обращение=Иван
Вы › /memory long profile language=русский
Вы › /memory long rules no_push=без явной команды
Вы › /memory long decisions database=PostgreSQL
Вы › /memory long knowledge deploy=через GitHub Actions
```

У долговременной памяти четыре раздела: `profile` — обращение, язык и стиль;
`rules` — правила и запреты проекта; `decisions` — устойчивые решения;
`knowledge` — знания о проекте. Пустое значение удаляет ровно выбранный ключ:

```text
Вы › /memory working срок=
Вы › /memory long rules no_push=
```

При включённой истории записи `working` и `long` участвуют в каждом запросе
независимо от выбранной стратегии контекста. `--no-history` отключает историю,
working-memory и проектную память, но сохраняет персонализацию. Порядок точный:
системный промпт → долговременный профиль →
долговременная память проекта → рабочая память → пересказ или картотека стратегии →
дословная часть краткосрочного диалога → новый вопрос. Поэтому данные текущей
задачи находятся ближе к вопросу, чем общие правила и профиль. В `/tokens` рабочая
и долговременная память показаны отдельными строками.

### Персонализация поверх памяти

`/profile` — короткая форма `/memory long profile`. Ключи профиля имеют структуру,
поэтому агент отличает обращение от стиля, формата и ограничений:

```text
Вы › /profile identity.address=Иван
Вы › /profile identity.language=русский
Вы › /profile style.tone=коротко и по делу
Вы › /profile format.answer=Markdown, сначала вывод
Вы › /profile constraints.no_push=не выполнять push без явной команды
```

Эти настройки автоматически добавляются к каждому пользовательскому запросу,
включая запуск с `--no-history`. Для разных типов задач можно задать свои правила.
`match` содержит фразы-триггеры через запятую; остальные ключи той же секции
попадают в промпт только при совпадении текущего запроса:

```text
Вы › /profile task.feature.match=напиши фичу,реализуй фичу
Вы › /profile task.feature.instructions=сначала исследователь, затем два исполнителя
Вы › /profile domain.shopping.match=собери корзину,подбери товары
Вы › /profile domain.shopping.instructions=сравни цену, рейтинг и доставку
```

Запрос «Напиши фичу импорта» активирует `task.feature`, а «Собери корзину для
пикника» — `domain.shopping`. Общие `identity`, `style`, `format` и `constraints`
действуют в обоих случаях. Старые плоские ключи вроде `обращение=Иван` продолжают
читаться и передаваться модели.

### Где память хранится

Краткосрочная и рабочая память принадлежат сессии. Они лежат вместе с ней в
`~/.llm-agent/sessions/`; рабочая память дополнительно сохраняется в снимках веток
и точек возврата. Возврат через `--resume` восстанавливает обе.

Долговременная память хранится отдельно:

- общий для всех проектов профиль — `~/.llm-agent/memory/profile.json`;
- правила, решения и знания текущего проекта — отдельный файл в
  `~/.llm-agent/memory/projects/`.

Проект определяется по ближайшему родительскому каталогу с `.git`, а вне Git —
по текущему каталогу. Имя проектного файла — хеш пути: данные одного проекта не
попадут в другой. Каталоги имеют права `0700`, файлы — `0600`; запись атомарная.
`/new`, `--rm-session` и `--no-save` не удаляют долговременную память.
Память — обычный текст, а не хранилище секретов: ключи с именами вроде
`api_key`, `*_token`, `*_password` и `private_key` программа отвергает. Секреты
держите в предусмотренных проектом файлах ключей или переменных окружения.

### Проверка до и после `/new`

Сценарий проверяется даже в бесплатном демонстрационном режиме — состояние видно
в `/memory`, поэтому не надо полагаться на формулировку ответа заглушки:

```text
$ agent --demo
Вы › Кодовое слово апельсин
Вы › /memory working задача=подготовить релиз
Вы › /memory long profile обращение=Иван
Вы › /memory
# short: есть диалог; working: задача; long: обращение

Вы › /new
Вы › /memory
# short: 0 сообщений; working: 0 записей; long: обращение=Иван осталось
```

На живой модели после `/new` вопрос «Что ты обо мне помнишь?» должен учитывать
обращение «Иван», но в новом запросе уже нет ни кодового слова, ни задачи релиза.

### Чем `/memory working` отличается от `/facts`

`/facts` — прежняя автоматическая картотека стратегии `facts`: модель сама
извлекает из разговора цели, решения и предпочтения, а блок уходит в запрос
только при `--strategy facts`. В картотеку может попасть и то, что предложила
сама модель, поэтому её можно просматривать и исправлять вручную.

`/memory working` — явная запись человека. Она не извлекается из разговора,
не зависит от стратегии и всегда уходит в модель, пока живёт текущая задача.
Обе механики существуют одновременно: `/facts` помогает сжать старый разговор,
а `working` фиксирует именно те данные задачи, которые человек решил сохранить.

## Стратегии управления контекстом

В окно модели влезает не всё, а разговор растёт. Что именно из накопившейся
переписки уходит в модель, решает стратегия — её выбирает человек, а не
программа.

| Стратегия | Что уходит в модель | Чем платит |
|---|---|---|
| `full` | вся переписка целиком | дороже всех и раньше всех упрётся в окно |
| `window` | последние N сообщений | не стоит ничего, но начало разговора забыто начисто |
| `facts` | картотека фактов + последние N | короткий служебный запрос на каждый вопрос |
| `summary` | пересказ начала + последние N | служебный запрос на каждые несколько сообщений |

```bash
agent --strategy window --keep-last 4    # только хвост переписки
agent --strategy facts                   # картотека важных сведений
agent --strategy full                    # как было до всяких стратегий
```

В разговоре стратегия переключается командой `/strategy`; без аргумента она
показывает все четыре рядом и помечает действующую. Переписка при переключении
не теряется: пересказ и картотека остаются на месте и снова работают, когда
вернётесь к своей стратегии.

**Сообщения не пропадают ни при одной стратегии.** Отложенное подменяется
только по дороге в модель: на экране, в `/history` и в файле сессии разговор
остаётся целым. Этим все четыре отличаются от обрезки (`on_overflow=trim`),
которая выбрасывает сообщения насовсем.

**Видно, что уходит.** В `/tokens` есть строка «Стратегия: …» и раскладка
запроса по частям — отдельными строками «Пересказ начала» и «Факты разговора».

| Поле | По умолчанию | Что задаёт |
|---|---|---|
| `history.strategy` | `summary` | как собирается запрос |
| `history.keep_last` | `6` | сколько последних сообщений уходит дословно |
| `history.facts.max_facts` | `20` | сколько фактов держать |
| `history.facts.max_tokens` | `300` | предел размера блока фактов в запросе |
| `history.facts.update_every` | `1` | после скольких вопросов обновлять картотеку |
| `history.compression.every` | `10` | сколько несжатых сообщений копится до пересказа |
| `history.compression.max_tokens` | `400` | предел длины самого пересказа |

### Скользящее окно — `--strategy window`

В модель уходят последние N сообщений, остальное просто не отправляется.
Ничего не стоит и ни к чему не обязывает, но начало разговора для модели
не существует.

Граница никогда не рвёт обмен пополам: хвост всегда начинается с вопроса
пользователя — ответ без своего вопроса модель прочла бы как ответ неизвестно
на что. Поэтому хвост бывает длиннее заказанного, но не короче.

При переполнении окно сужается, а сообщения остаются: выбрасывать их
бессмысленно — окно отсчитывается от конца, и на место выброшенной пары
втянулась бы пара постарше.

### Картотека фактов — `--strategy facts`

Отдельный блок «ключ — значение» с тем, что понадобится дальше: цель,
ограничения, решения, договорённости, предпочтения. В модель уходит картотека
плюс последние N сообщений.

```
Важные сведения из этого разговора, собранные по ходу:
- платформа: Android, iOS не делаем
- бюджет: 300 тысяч рублей
- срок: к 1 марта, дата жёсткая
```

**Картотеку ведёт модель.** После каждого вопроса пользователя уходит короткий
запрос: вот картотека, вот новые сообщения — обнови. В `/stats` его расход
виден строкой «факты». Реже — `--set history.facts.update_every=2`.

**Забытое моделью не пропадает.** Ответ сливается с прежней картотекой, а не
заменяет её: модель, которую попросили перечислить всё, один-два факта всё
равно опустит. Забыть факт можно намеренно — пустым значением.

**Картотеку видно и можно поправить.** Команда `/facts` показывает её целиком;
`/facts срок=к 1 марта` записывает факт руками, `/facts срок=` забывает,
`/facts update` просит модель обновить сейчас, `/facts reset` очищает.

**Если модель ответила не JSON** — ответ на вопрос всё равно будет: в запрос
уйдёт прежняя картотека, а причина покажется в `/facts` и `/tokens`. После
каждой неудачи подряд пауза перед следующей попыткой удваивается: платить за
одну и ту же неудачу на каждом вопросе незачем.

### Ветки диалога

Ветвление — не пятая стратегия, а отдельная механика: оно работает при любой
из четырёх. Смысл в том, чего нельзя сделать линейным разговором: обсудить два
несовместимых решения от одного и того же места, не давая модели видеть
соседний вариант.

```
/checkpoint выбор-стека     запомнить место разговора
/branch нативная            отвести ветку и продолжать в ней
/branch кросс выбор-стека   вторая ветка от той же точки
/branches                   список веток и точек возврата
/switch нативная            вернуться в первую
```

Точка возврата хранит снимок переписки, а не номер сообщения: номер не
переживает обрезки, а снимок переживает. Расход при этом общий — два
продолжения оплачивал один кошелёк, и `/stats` показывает итог по всем веткам.
Ветки и точки ложатся в файл сессии: `-r` возвращает и их, и ту ветку, в
которой вы были.

### Четыре стратегии рядом — `./context.sh`

```bash
./context.sh                                       на заглушке, бесплатно
./context.sh --live --provider groq --max-tokens 250   бесплатный тариф
./context.sh --only facts --rounds 20 --step       одна стратегия, по шагам
```

Один и тот же сбор ТЗ ведётся всеми четырьмя стратегиями: вопросы одинаковые,
окно одинаковое, модель одна. Пять сведений — платформа, бюджет, срок, решение
по входу и предпочтение — названы по разу и расставлены по разговору; в конце
четыре из них спрашиваются обратно. В конце показа — ветвление: две ветки от
одной точки и один и тот же вопрос в каждой.

Живой прогон на Groq (`qwen/qwen3.8-27b`, бесплатный тариф), окно 3 000,
предел ответа 250 токенов, 14 вопросов, `keep_last=4`:

| Стратегия | Вход | Запросов | Вход на последнем | Помнит |
|---|---|---|---|---|
| full | 31 955 | 18 | 2 518 | 2 из 4 |
| window | 9 190 | 18 | **533** | 0 из 4 |
| facts | 22 192 | 36 (+18 служ.) | 832 | **4 из 4** |
| summary | 23 323 | 23 (+5 служ.) | 1 567 | 2 из 4 |

Главное здесь — последний столбец рядом с первым. **Окно вдвое дешевле всех
и не помнит ничего. Картотека помнит всё названное и стоит почти как полная
история** — служебные запросы съедают почти всю экономию, зато вход на
последнем вопросе втрое ниже и с длиной разговора не растёт.

Полная история ответила на два вопроса из четырёх, хотя все сведения были в
запросе: они утонули в четырнадцати ответах. Пересказ — тоже на два: срок и
решение по входу растворились в прозе. Это и есть разница между прозой и
картотекой — факт с ключом либо есть, либо его нет.

Ветвление в том же прогоне: две ветки от точки «выбор-стека» с решениями
«нативно на Kotlin» и «на Flutter», и на общий вопрос «на чём договорились»
каждая ответила своим, не упомянув решение соседней.

Качество и память проверяются только на живой модели: заглушка отвечает
заготовленным текстом и «помнит» одинаково при любой стратегии, а объекта JSON
для картотеки не возвращает вовсе.

## Сжатие истории — `--strategy summary`

Каждый вопрос отправляет всю переписку заново — поэтому десятый стоит вчетверо
дороже первого, набранный теми же словами. Сжатие возвращает эту цену к началу:
старое начало разговора заменяется пересказом, последние сообщения уходят
дословно.

**Работает само.** Это стратегия по умолчанию, и с умолчаниями первый пересказ
случается на восьмом обмене. Короткий разговор за него не платит.

```bash
agent --no-compress                  # то же, что --strategy full
agent --keep-last 4 --compress-every 6
agent --set history.compression.max_tokens=250
```

**Сообщения не пропадают.** Пересказ подменяет начало только по дороге в
модель: на экране, в `/history` и в файле сессии разговор остаётся целым.
Этим сжатие и отличается от обрезки, которая выбрасывает сообщения насовсем.

**Видно, что оно даёт.** В `/tokens` появляется часть «Пересказ начала» и
строка вида «10 сообщений не уходят в модель: вместо них пересказ на 49 ·
вместо 255: экономия 206 на каждом запросе». Сам пересказ показывает
`/summary`, а `/compress` сворачивает начало, не дожидаясь порога.

**За пересказ платят отдельно.** Его пишет та же модель отдельным запросом, и
в `/stats` он виден строкой «сжатие — 1 запрос». Один такой запрос раз в
десяток сообщений окупается тем, что начало разговора больше не уходит в
модель каждый раз.

**При переполнении сжатие пробуется раньше обрезки.** Если запрос не влезает,
начало сворачивается в пересказ, даже когда порог ещё не набрался: обрезка
теряет начало насовсем, а пересказ его сохраняет. Не влезло и после сжатия —
работает прежняя политика: отказ или `on_overflow=trim`.

**Если пересказ не получился** — ответ на вопрос всё равно будет: в запрос
уйдёт вся история, как раньше, а причина покажется в `/tokens` и `/summary`.
Повторная попытка идёт не на следующем же вопросе, а когда накопится следующий
кусок: неудачный запрос тоже оплачен.

### Три способа рядом — `./compress.sh`

```bash
./compress.sh                                  на заглушке, бесплатно
./compress.sh --live --provider groq           настоящие запросы, бесплатный тариф
./compress.sh --window 6000 --rounds 20 --step своё окно и длина, по шагам
```

Один и тот же разговор ведётся трижды: со всей историей, с обрезкой и со
сжатием. Вопросы одинаковые, окно одинаковое. Имя названо в первом сообщении,
город — в середине, оба спрашиваются в конце.

Живой прогон на Groq (бесплатный тариф, окно 4 000, 12 вопросов):

| Способ | Ответов | Вход | Выход | Запросов | Вход на последнем | Помнит |
|---|---|---|---|---|---|---|
| Вся история | 5 | 5 635 | 3 491 | 5 | 2 771 | 0 из 2 |
| Обрезка | 14 | 29 366 | 11 926 | 16 | 2 151 | 0 из 2 |
| Сжатие | 14 | 43 216 | 13 350 | 24 (+8 сжатие) | 2 443 | **2 из 2** |

Главное в этой таблице — последний столбец. **Имя и город помнит только
сжатие.** Полная история встала на шестом вопросе, обрезка дошла до конца, но
выбросила 22 сообщения вместе с именем — на вопрос «как меня зовут» модель
ответить уже не может.

Вход на общем пятом шаге: 2 771 токен без сжатия против 2 267 со сжатием — на
18% меньше. За первые пять вопросов потрачено 9 126 токенов без сжатия против
7 708 со сжатием, и запросы за пересказом в это уже включены.

Обрезка по расходу бывает и дешевле сжатия — она просто забывает и ни за какие
пересказы не платит. Разница в том, что забытое ею не хранится нигде.

Качество ответов сравнивается только на живой модели: заглушка отвечает
заготовленным текстом и «помнит» одинаково при любом способе, поэтому без
`--live` столбец «Помнит» пустой.

### Ввод и вставка из буфера

Строка ввода умеет то же, что обычная строка терминала: стрелки, Home/End,
история набранного по стрелке вверх.

**Многострочная вставка уходит одним сообщением.** Само по себе это не работает:
терминал отдаёт вставленный текст как обычный набор, и перевод строки внутри
вставки неотличим от нажатия Enter — каждая строка уезжала в модель отдельным
запросом. Программа дочитывает остаток вставки сама, поэтому вставленный кусок
попадает в одно сообщение целиком.

### Параметры генерации

Их можно переключать прямо во время диалога, не перезапуская программу.
Изменённое действует для всех последующих запросов.

```
/change_llm_params                                  показать текущие значения
/change_llm_params max_tokens=200 temperature=0.3   изменить
/change_llm_params stop=###КОНЕЦ###|STOP            несколько стоп-строк через |
/change_llm_params response_format=json_object      структурированный вывод
/reset_llm_params                                   вернуть значения по умолчанию
```

| Параметр | Что делает | Допустимо |
|---|---|---|
| `max_tokens` | предел длины ответа | от 1 до 32000 |
| `temperature` | случайность ответа | от 0 до 2 |
| `top_p` | доля самых вероятных продолжений, из которых идёт выбор | от 0 до 1 |
| `stop` | строки, обрывающие генерацию | до четырёх, через `|` |
| `response_format` | режим вывода на стороне провайдера | `json_object`, `text`, `none` |

#### temperature и top_p

Оба управляют разбросом ответов, но по-разному. `temperature` меняет сами
вероятности: чем выше, тем охотнее модель берёт менее очевидные слова. `top_p`
вероятности не трогает, а отсекает хвост: при `top_p=0.1` выбор идёт только
из самых вероятных продолжений, составляющих десять процентов вероятности.

Общее правило — крутить что-то одно. Вместе они дают трудно предсказуемый
результат.

Допустимый предел температуры **зависит от провайдера**, единого стандарта нет.
Программа принимает от 0 до 2 — это соглашение OpenAI, по чьему протоколу
работают все восемь провайдеров. У YandexGPT в документации диапазон 0–1, и
значение выше единицы там может быть отвергнуто. GigaChat в проверке принял
даже 5, но пользы в этом нет: уже при 2 ответ начинает разваливаться, а при 5
смешиваются алфавиты. Предел в 2 оставлен как разумное ограждение.

```
/change_llm_params temperature=0    предсказуемо, почти всегда один ответ
/change_llm_params temperature=1.5  разнообразно, годится для идей
/change_llm_params top_p=0.1        разброс срезан, температуру не трогаем
/change_llm_params top_p=1          отсечения нет
```

#### stop

Список строк, при появлении которых провайдер обрывает генерацию. Сама строка
в ответ не попадает. Сравнение идёт **буквально по символам**, а не по смыслу.

```
/change_llm_params stop=###КОНЕЦ###        оборвать на маркере
/change_llm_params stop=Вопрос:|Ответ:     оборвать, если модель начнёт диалог сама с собой
/change_llm_params stop=\n\n               оборвать на пустой строке
/change_llm_params stop="Шаг 2:"           значение с пробелами — в кавычках
/change_llm_params stop=none               снять ограничение
```

Несколько строк перечисляются через `|`, их не больше четырёх. Перенос строки
и табуляция записываются как `\n` и `\t`.

#### response_format

Просит провайдера выдать структурированный ответ. Поддерживается не всеми.

```
/change_llm_params response_format=json_object   только валидный JSON
/change_llm_params response_format=text          обычный текст
/change_llm_params response_format=none          не передавать параметр вовсе
```

Разница между `text` и `none`: в первом случае параметр уходит со значением
`text`, во втором не уходит совсем. Для большинства провайдеров результат
одинаковый, но если провайдер спотыкается на самом параметре, помогает `none`.

Просить JSON стоит вместе с инструкцией в самом вопросе: параметр обязывает
провайдера вернуть валидный JSON, но не описывает, какие в нём должны быть поля.

**Слово «json» должно встречаться в самом запросе.** OpenAI, DeepSeek и Groq
иначе отвечают отказом `400` — они не берутся угадывать за модель, чего от неё
хотят. Программа это отслеживает: если провайдер отказал по такой причине,
в запрос добавляется требование ответить в формате JSON, запрос повторяется,
и в ответе появляется пометка «Запрос подправлен». Требование провайдера
запоминается, поэтому лишний отказ случается только на первом сообщении.

#### Почему нет top_k

`top_k` нет в протоколе OpenAI, на котором работают все восемь провайдеров.
Передать его можно только «мимо» схемы запроса, и провайдер молча его
проигнорирует — при этом ошибки не будет, что хуже отказа.

Проверено опытом: при температуре 2 и шести запросах подряд `top_p=0.01` схлопнул
ответы до одного варианта, а `top_k=1` оставил два — то есть не подействовал,
хотя запрос прошёл успешно. Добавлять ручку, которая ничего не делает, вреднее,
чем её не иметь.

Изменённые параметры видны в счётчиках внизу экрана отдельной строкой,
а `max_tokens` дополнительно меняет резерв под ответ: уменьшив его, вы
освобождаете место под историю диалога.

Два замечания, найденные живой проверкой. Если ответ упёрся в `max_tokens`,
программа скажет об этом прямо — иначе обрыв на полуслове выглядел бы как
странный ответ модели. И если провайдер не примет параметр, он будет убран
из запроса, а вы увидите предупреждение: молча делать вид, что параметр
применился, программа не станет.

`Ctrl+C` во время ожидания ответа отменяет запрос, не выходя из программы.
`Ctrl+D` — выход.

## Если что-то не работает

| Что видно на экране | Что делать |
|---|---|
| `Ключ отклонён провайдером (401)` | ключ неактуален или скопирован не целиком |
| `Недостаточно средств на аккаунте провайдера (402)` | ключ рабочий, но баланс нулевой — пополнить или запустить `--demo` |
| `Ключ авторизации не принят (400)` | GigaChat отвечает так и на обрезанный, и на недействительный ключ — сверьте строку Base64 и scope |
| `Не пройдена проверка TLS-сертификата` | установите сертификат НУЦ Минцифры (команда выше) |
| `В ключе есть символы вне латиницы` | при копировании попала кириллическая буква — скопируйте ключ заново |
| `Вместо ответа API пришла HTML-страница` | запрос перехватил корпоративный прокси; добавьте домен провайдера в `NO_PROXY` |
| `Модель не найдена (404)` | модель недоступна вашему аккаунту |
| `Не удалось связаться с API` | нет сети, либо провайдер недоступен из вашего региона |

## Управление ответом модели

Отдельный инструмент отправляет **один и тот же вопрос пять раз**, каждый раз
отдельным запросом без истории. От шага к шагу добавляется **ровно один рычаг**,
а не сумма предыдущих: иначе непонятно, что именно подействовало.

```bash
./compare.sh              # подряд, одним экраном
./compare.sh --step       # по шагам, между экранами ждёт Enter
./compare.sh --demo       # без обращения к сети
```

Вопрос во всех пяти шагах один: «Приведи список наиболее успешных книг Нассима
Талеба». Температура тоже одна на все шаги — иначе сравнение было бы нечестным.

| Шаг | Рычаг | Как задан |
|---|---|---|
| 1 | ничего | только вопрос, `max_tokens` = резерв модели |
| 2 | формат в промпте | инструкция: ответ — фрагмент HTML с таблицей `<table>` |
| 3 | формат через API | `response_format={"type": "json_object"}`, схему не описываем |
| 4 | условие завершения | `stop` — тот же промпт с параметром и без него |
| 5 | ограничение длины | `max_tokens=120` и больше ничего |

По каждому шагу видно **отправленный запрос целиком** — сообщения и параметры, —
**ответ целиком** (длинный разбивается на страницы), измерения и проверку.

### Проверки считает код, а не глаз

У каждого шага своя проверка разбором ответа:

* шаг 2 — ответ парсится `html.parser`: есть `<table>`, есть строки, нет текста
  вне разметки, нет обрамления в тройные кавычки;
* шаг 3 — проходит `json.loads`, и отдельно показывается, **какие ключи придумала
  модель**: `response_format` гарантирует синтаксис, но не схему;
* шаг 4 — сравнение двух ответов: `finish_reason`, наличие стоп-строки в тексте,
  число пунктов и число токенов;
* шаг 5 — `finish_reason == "length"` и обрыв на полуслове.

### Шаг 4: условие завершения должно быть видно

`stop` срабатывает только тогда, когда модель действительно напечатала эту
строку. Поэтому стоп-последовательность взята не выдуманная, а такая, которую
модель печатает сама, — начало четвёртого пункта нумерованного списка. Промпт
у обоих запросов совпадает **до символа**, меняется один параметр:

| Запрос | Параметры | Что вышло на живом прогоне |
|---|---|---|
| 4а | `stop` не передаётся | 5 пунктов, 224 токена |
| 4б | `stop=["\n4.", "\n4)", "\n**4"]` | 3 пункта, 133 токена |
| 4в | договорный маркер `%%END%%` | 1 пункт, 65 токенов |

Стоп-строки привязаны к началу строки: без переноса `4.` поймало бы и год `2004.`
внутри предложения. Вариантов три, потому что нумерацию модель оформляет
по-разному. DeepSeek принимает до шестнадцати стоп-строк, программа ограничивает
себя четырьмя — общий предел для всех провайдеров.

Запрос 4в показывает, как это делают в проде: модель просят печатать маркер
`%%END%%` после каждой книги, и он же передаётся в `stop`. Виден и предел приёма
— маркер появляется в тексте только потому, что мы о нём попросили, то есть
жёсткий обрыв держится на послушности модели. До пользователя маркер не доходит:
провайдер срезает его вместе с хвостом.

Кириллический маркер брать не стоит: модель разбивала `###КОНЕЦ###` на части
и вставляла перенос строки, после чего стоп-последовательность не срабатывала
вовсе.

### Что показал живой прогон на DeepSeek

| Шаг | Символов | Токенов | Завершение | Проверок |
|---|---|---|---|---|
| 1 — ничего | 4203 | 1345 | stop | 1/1 |
| 2 — формат в промпте | 862 | 324 | stop | 5/5 |
| 3 — формат через API | 703 | 238 | stop | 3/3 |
| 4 — условие завершения | 419 | 133 | stop | 6/6 |
| 5 — ограничение длины | 402 | 120 | **length** | 2/2 |

Выводы из этих чисел:

* **инструкция в промпте** — единственный рычаг, который задаёт структуру, но
  держится на послушности модели;
* **`response_format=json_object`** гарантирует синтаксис, а не схему: имена
  полей модель выбрала сама (`books` → `title, year, success`), так что описание
  схемы из промпта никуда не девается;
* **`stop`** обрывает генерацию на стороне провайдера — тот же промпт даёт пять
  пунктов без параметра и три с ним, — но сработает только если модель напечатает
  эту строку, а сама строка в ответ не попадёт;
* **`max_tokens`** не сокращает ответ, а режет его на полуслове: это страховка
  от расходов, а не способ получить короткий ответ. За краткость отвечает
  инструкция.

## Четыре способа спросить одно и то же

Отдельный инструмент решает **одну задачу четырьмя способами** и сравнивает
результаты.

```bash
./reasoning.sh                       ответы и оценка одной моделью
./reasoning.sh --judge gigachat      качество оценивает другой провайдер
./reasoning.sh --runs 3              три прогона каждого способа
./reasoning.sh --temperature 0.5     другая случайность ответов
./reasoning.sh --demo                без обращения к сети
```

| Способ | Что меняется в промпте |
|---|---|
| Прямой вопрос | ничего не добавляется |
| Пошаговое решение | просьба разбить на шаги и показать промежуточные вычисления |
| Промпт от самой модели | модель сначала пишет промпт для решения, затем решает по нему |
| Три эксперта по отдельности | инженер-математик, учитель литературы и медик-инфекционист отвечают независимо, каждый своим запросом |

Сравниваются **две разные вещи**. Верность итога считает код: у задачи есть
заранее вычисленный ответ. Качество объяснения — полноту, ясность,
обоснованность — оценивает **другая модель**, потому что своя оценка своему же
ответу была бы слабым доводом.

Два решения, без которых сравнение было бы нечестным. Итоговое число из ответа
достаёт отдельным запросом модель, а не регулярное выражение: разбор свободного
текста хватал промежуточные числа — из фразы «3 раза для числа 777» получалось
`3` вместо `603`. И обрыв ответа по лимиту показывается отдельным столбцом:
сравнивать недоговорённый ответ с дошедшим до конца нельзя.

Один прогон ничего не доказывает — ответы модели разбросаны от запуска к
запуску. Поэтому `--runs N` повторяет каждый способ и сводит результат.

## Инварианты и ограничения состояния

Инварианты задаются в конфиге отдельно от переписки. Они не извлекаются из
слов пользователя, не сжимаются вместе с историей и не исчезают после `/new`:

```yaml
invariants:
  rules:
    - id: architecture.modular-monolith
      category: architecture
      rule: Система остаётся модульным монолитом; новые микросервисы запрещены
      reason: Команда не готова поддерживать распределённую инфраструктуру
    - id: stack.python
      category: stack
      rule: Серверная часть пишется на Python 3.12 с FastAPI
      reason: Это поддерживаемый командой серверный стек
```

Доступны четыре категории: `architecture`, `technical-decision`, `stack` и
`business-rule`. Полный пример лежит в `configs/invariants.yaml`.

Их можно задать прямо во время диалога, в том числе при запуске с дефолтным
конфигом:

```text
В проекте используем только Kotlin. Java использовать нельзя.
```

Агент распознает явную долгоживущую декларацию, сохранит нормализованное
правило и покажет его `id`. Уже текущий ответ строится с учётом нового
инварианта, а следующий запрос на Java будет отклонён. Разовые указания вроде
«ответь только кратко» анализируются, но инвариантом не становятся.

Для точного ручного управления остаются команды:

```text
/invariant add stack stack.python Сервер только на Python | Командный стандарт
/invariant add architecture architecture.monolith Система остаётся монолитом
/invariant
```

Повторный `add` с тем же `id` заменяет правило. Удаление и полная очистка:

```text
/invariant remove stack.python
/invariant clear
```

Такие правила сразу входят в системный контекст следующих ответов, переживают
`/new` и сохраняются при выходе из сессии.

Автораспознавание включено по умолчанию. Его можно отключить, сохранив ручные
команды и правила из файла:

```yaml
invariants:
  auto_detect: false
```

Каждый запрос проходит отдельную проверку до основного ответа. Если просьба
сама требует нарушить правило, основная генерация не запускается: агент
называет `id`, приводит доверенный текст правила и объясняет конкретный
конфликт. Совместимый запрос получает обычный ответ, но перед выдачей ответ
проверяется ещё раз. Нарушающий вариант заменяется объяснённым отказом.
Предложенные моделью вызовы инструментов также проверяются до исполнения;
конфликтующий вызов до обработчика не доходит.

В JSON-результате ход проверки виден явно:

```json
{
  "refused": true,
  "invariant_checks": [{"phase": "request", "status": "refused"}],
  "invariant_violations": [{"id": "stack.python", "category": "stack"}]
}
```

Автоматически найденные правила дополнительно возвращаются в поле
`detected_invariants`.

Контролёр отвечает только JSON и может ссылаться лишь на `id` из конфига.
Неразбираемый или противоречивый вердикт останавливает запрос: при неизвестном
состоянии агент не выпускает потенциально нарушающее решение. Проверки видны
в статистике отдельной строкой `инварианты`.

Проверить конфликт на настоящей модели:

```bash
./run.sh --config invariants
# Вы › Перепиши сервер на Go и вынеси оплату в отдельный микросервис
```

Подробнее: [docs/feature-invariants.md](docs/feature-invariants.md).

## Агент

Всё, что делает программа между вашим вопросом и ответом на экране, упаковано
в отдельный пакет `llmagent`. Он не печатает, ни о чём не спрашивает и не знает
о существовании интерфейса — поэтому одного и того же агента вызывают чат,
опыты со сравнением промптов и массовый прогон на сотню конфигов.

```python
from llmagent import Agent, DEFAULT_CONFIG

agent = Agent(DEFAULT_CONFIG)          # ChatGPT gpt-5.4-mini
result = agent.ask("Привет!")
print(result.text, result.total_tokens, result.cost)
```

Внутри по порядку: входная политика, история диалога, обращение к провайдеру,
выходная политика с переспросом, судья и учёт расхода.

### Конфиг

Всё поведение агента — данные, а не ветки в коде. Что отличает одного агента
от другого, то и есть поле конфига.

| Часть | За что отвечает |
|---|---|
| `provider`, `model`, `api_key`, `api_extra` | куда идти и чем авторизоваться |
| `system_prompt` | кем агент себя считает |
| `generation` | `max_tokens`, `temperature`, `top_p`, `stop`, `response_format` |
| `input` | длина запроса, запрещённые подстроки, шаблон, обрезка вместо отказа |
| `output` | формат и схема ответа, договорный маркер, число переспросов |
| `judge` | признаки оценки, шкала, порог и **свой конфиг агента-оценщика** |
| `history` | помнить диалог или отвечать каждый раз с чистого листа |
| `budget` | потолок по токенам, деньгам и числу запросов |
| `transport` | заглушка вместо сети и длина её паузы |

Конфиг замо́рожен: поменять его на ходу нельзя, но можно получить новый —
на этом и держатся `/change_model` и `/change_llm_params`.

```python
Agent(DEFAULT_CONFIG.with_changes(model="gpt-5.4", generation=...))
Agent(AgentConfig.from_file("configs/books-json.yaml"))
Agent(AgentConfig.from_dict(payload))      # например, из тела HTTP-запроса
```

Тот же конфиг понимает и чат:

```bash
./run.sh --config configs/books-json.yaml
```

Готовые примеры лежат в [configs/](configs/). Команда `/config` печатает
действующий конфиг в том же виде, в каком его можно сохранить в файл — ключ
в выводе заменён на `***`, чтобы конфиг можно было показывать и пересылать.

### Правки конфига при запуске

Конфиг — основа, а команда запуска накрывает его сверху. Названное поле
меняется, остальные остаются как были.

```bash
agent --model gpt-5.4-nano --max-tokens 150      # подешевле и покороче
agent --format json --set attempts=3             # строго JSON, с переспросом
agent --max-cost 0.05                            # не тратить больше пяти центов
agent --no-history                               # каждый вопрос сам по себе
agent --set template="Переведи на английский: {input}"
```

Частые поля имеют короткий флаг:

| Флаг | Что задаёт |
|---|---|
| `--model`, `--provider` | модель и сервис; провайдер определяется по имени модели |
| `--temperature`, `--max-tokens` | разброс ответов и предел их длины |
| `--system-prompt`, `--append-system-prompt` | кем агент себя считает; второй дописывает к первому |
| `--format` | требуемая форма ответа: `free`, `json`, `yaml`, `md` |
| `--max-cost` | потолок трат за сессию; запрос не уйдёт, если превысит его |
| `--no-history` | отвечать без истории диалога; профиль сохраняется |
| `--no-compress` | не сжимать историю: вся переписка уходит целиком |
| `--keep-last`, `--compress-every` | сколько сообщений уходит дословно и когда обновлять пересказ |
| `--agent-name` | подпись агента (видна в панелях под-агентов) |

Остальные поля — через `--set`, сколько нужно раз. У частых есть и короткие
имена: `--set temperature=0.2` работает так же, как `--set generation.temperature=0.2`.

```bash
agent --set output.require_valid=true --set judge.min_mean=4 --set input.max_chars=500
```

**Что победит, если задать поле дважды:** от общего к частному — конфиг, затем
флаг, затем `--set`. Проверить результат:

```bash
agent --config frugal --temperature 0.2 --show-config
```

Печатает собранный конфиг целиком и выходит; жёлтым отмечено то, что
отличается от значений по умолчанию, ключ заменён на `***`.

Конфиг можно задать и строкой, без файла:

```bash
agent --config '{"model": "gpt-5.4-nano", "budget": {"max_cost": 0.01}}' --ask "..."
```

Полный перечень полей с объяснением каждого — в
[docs/plan-config-overrides.md](docs/plan-config-overrides.md).

### Сессии

Программа задумана как терминальный инструмент: положите её в PATH и зовите
из любого каталога.

```bash
ln -s "$(pwd)/agent" ~/.local/bin/agent
agent                  # новая сессия
agent --config frugal  # новая сессия на готовом конфиге
```

**Каждый запуск — своя сессия со своей краткосрочной и рабочей памятью.**
Идентификатор сессии виден в шапке. Два терминала не делят историю, рабочие
данные и счётчики; явно сохранённый долговременный профиль и память текущего
проекта у них общие.

```
терминал 1                         терминал 2
$ agent                            $ agent
💬 Сессия 7f3a501d                 💬 Сессия 46492518
Вы › Привет, меня зовут Влад       Вы › Как меня зовут?
🤖 Приятно познакомиться!          🤖 Не знаю, ты не сообщал.
Вы › Как меня зовут?
🤖 Тебя зовут Влад.
```

Диалог сохраняется после каждого ответа, поэтому в него можно вернуться:

```bash
agent --continue           # в самую свежую сессию
agent --resume 7f3a501d    # в названную
agent --sessions           # список: когда, модель, обменов, тема
agent --rm-session 7f3a501d    # удалить одну
agent --rm-session all         # удалить все
agent --no-save            # не сохранять эту сессию
```

**Что лежит на диске.** Переписка, рабочая память, счётчики расхода и конфиг —
файлами в `~/.llm-agent/sessions/`, по файлу на сессию, доступными на чтение
только вам. Долговременная память лежит отдельно в `~/.llm-agent/memory/` и
не удаляется вместе с сессией. **Ключ провайдера в файлы не попадает**: при
сохранении он обнуляется, при возврате берётся заново из окружения или из файла
рядом.

Одиночные запросы через `--ask` не сохраняются — иначе каждый вызов
под-агента оставлял бы файл. Читать сохранённую сессию они при этом умеют:
`--continue --ask "…"` задаст вопрос в контексте прошлого разговора.

Смена модели и параметров записывается сразу, не дожидаясь следующего ответа:
переключить модель и выйти — обычное дело, и возврат вернёт именно её.

Вернувшись в сессию, настройки можно поменять: `--resume 7f3a501d --model gpt-5.4`
продолжит тот же разговор на другой модели.

### Один вопрос без диалога

```bash
agent --config frugal --ask "Что такое хороший код"          # ответ текстом
agent --config frugal --ask "Что такое хороший код" --json   # итог объектом JSON
```

В режиме `--json` в stdout уходит только объект JSON и ничего больше —
поэтому его можно разбирать из скрипта. Вопросов в консоль этот режим не
задаёт: не нашлось реквизитов — сразу ошибка с кодом возврата 3.

Сохранённую сессию он читает, но не записывает:

```bash
agent --continue --ask "Как меня зовут?"     # спросить в контексте прошлого разговора
```

### Под-агенты

Агент умеет вызвать внутри себя другой агент — той же командой, в отдельном
процессе, с выбранным конфигом.

```
Вы › /agent books-json Книги Нассима Талеба

╭─ ⤷ Под-агент books-json ────────────────────────────────────╮
│ Сессия  e2958002 · своя память, отдельный процесс           │
│ Модель  ChatGPT (OpenAI) · gpt-5.4-mini                     │
│ Расход  2.4 с · 214 ток. · $0.0006                          │
│                                                             │
│ {"items": [{"name": "Чёрный лебедь", "year": 2007, …        │
│                                                             │
│ Ответ принят в память этой сессии — на него можно           │
│ ссылаться следующим вопросом.                               │
╰─────────────────────────────────────────────────────────────╯
```

Под-агент — **отдельный процесс**, поэтому изоляция получается не на
обещании, а на устройстве: своя память, свои счётчики, своё падение. Родителю
возвращается только итог. Он ложится в память вызвавшей сессии помеченной
заметкой — модель сможет на него ссылаться, но не спутает со своим ответом,
а расход под-агента идёт в общий счёт отдельной строкой:

```
Запросов к API   3
Из них           основной — 1 запрос · служебный — 1 запрос · под-агент — 1 запрос
```

Ключ провайдера передаётся дочернему процессу **переменной окружения**, а не
аргументом командной строки: argv виден в выводе `ps` любому процессу
пользователя.

Первое слово после `/agent` — имя конфига, дальше вопрос. Конфиг можно
поправить на месте — до `--` правки, после вопрос:

```
Вы › /agent frugal temperature=0.1 max_tokens=80 -- Что такое хороший код
```

`/agent` без аргументов показывает список конфигов из [configs/](configs/).

### Модель зовёт под-агента сама

Если в конфиге включён инструмент `spawn_agent`, решение о вызове принимает
уже не человек, а модель:

```bash
agent --config orchestrator
```

```
Вы › Дай ровно пять книг Нассима Талеба строгим JSON по схеме

╭─ 🔧 Модель сама вызвала под-агента books-json ───────────────╮
│ ╭─ ⤷ Под-агент books-json ────────────────────────────────╮ │
│ │ Сессия  91d00506 · своя память, отдельный процесс       │ │
│ │ Расход  2.1 с · 497 ток. · $0.000905                    │ │
│ │ {"items":[{"name":"Одураченные случайностью",…          │ │
│ │ Этот ответ модель получила себе и учла в своём.         │ │
│ ╰─────────────────────────────────────────────────────────╯ │
╰─────────────────────────────────────────────────────────────╯
╭─ 🤖 gpt-5.4-mini ───────────────────────────────────────────╮
│ {"items":[{"name":"Одураченные случайностью","year":2001,…  │
╰────────────────────── 1.7 с · 611 → 133 ток. · $0.0011 ────╯
```

Инструменты — тоже поле конфига:

```bash
agent --set 'tools.enabled=[spawn_agent]' --set tools.max_calls=2
```

| Поле | Что задаёт |
|---|---|
| `tools.enabled` | какие инструменты модель вправе вызывать; пусто — она о них не узнает |
| `tools.max_calls` | сколько кругов «просит вызов — отвечаем» допустимо за один ответ |

Предел обязателен: модель может звать инструмент без конца. На последнем круге
инструменты ей не предлагаются вовсе, а вместо них приходит прямое сообщение,
что вызовы кончились — предлагать то, чем уже нельзя пользоваться, значит
выпрашивать пустой ответ.

Расход под-агента идёт в общий счёт отдельной строкой — и когда его зовёт
человек, и когда модель:

```
Запросов к API   3
Из них           основной — 1 запрос · инструмент — 1 запрос · под-агент — 1 запрос
```

Инструменты умеют не все модели. `groq/compound`, например, отвечает отказом —
агент переводит его в понятный текст и предлагает сменить модель или убрать
инструменты из конфига.

### Сто агентов с разными конфигами

```bash
./spawn.sh --agents 100
```

```
Создано и опрошено         100 агентов
Ответили                   100
Соединений открыто         8 на 100 агентов
Времени с начала до конца  0.07 с
```

Сто агентов, 26 моделей восьми провайдеров, у каждого свой системный промпт,
своя температура и свой набор политик. Ни одного вопроса человеку: реквизиты
берутся из конфига или из окружения. Прогон идёт на заглушке и бесплатен;
`--live` шлёт настоящие запросы и сначала спрашивает подтверждение.

### Тесты

```bash
./test.sh        # полный набор тестов на локальных заглушках
./test-mcp.sh    # обязательный Agent -> MCP -> fake GitHub HTTP E2E
./livecheck.py   # живая проверка: настоящие запуски из терминала
```

`./livecheck.py` проверяет не части, а то, что делает человек: запускает
команду с разными параметрами, разговаривает, зовёт под-агента, возвращается
в сессию. Каждый сценарий подписан требованием, которое он подтверждает.

```bash
./livecheck.py                        на заглушке, бесплатно
./livecheck.py --live                 настоящие запросы к Groq — бесплатный тариф
./livecheck.py --live --provider openai   платно, поэтому спросит подтверждение
```

Живой режим по умолчанию идёт к Groq: у него бесплатный тариф, поэтому
подтверждения он не требует и денег не стоит. Тариф ограничивает частоту, и
на отказ 429 проверка ждёт и пробует снова — это про тариф, а не про агента.

У платного провайдера проверка сначала спросит согласие, а в конце покажет,
сколько потратила. Прогон по OpenAI на `gpt-5.4-mini` — двадцать сценариев,
около полутора центов.

Сеть для тестов не нужна, денег они не тратят: везде подставлена заглушка.

Ввод с клавиатуры проверяется через настоящий терминал (pty) — в канал его
подать нельзя, и потому дефект со склеиванием сообщений дожил до жалобы.

Два сторожа следят за тем, что уже однажды сломалось. Первый — за изоляцией:
если в `llmagent` появится импорт `rich`, `llmchat` или вызов `print`, тест
упадёт. Второй — за настоящим `~/.llm-agent`: любой тест, оставивший там след,
роняет прогон. Оба появились после того, как соответствующая ошибка случилась
на самом деле.

## Демонстрационный ролик

В каталоге `demo/` лежит инструмент, который записывает работу приложения
в видеофайл, проходя весь сценарий: выбор LLM, запрос токена, вопрос модели,
проверку памяти диалога и статистику по токенам.

```bash
python3 -m venv .venv-demo
.venv-demo/bin/pip install -r demo/requirements.txt

# работа чата: выбор LLM, вопрос, память диалога, счётчики
.venv-demo/bin/python demo/record_demo.py --key-file ~/.gigachat-key

# параметры генерации: один вопрос, разные настройки
.venv-demo/bin/python demo/record_params_demo.py --key-file ~/.gigachat-key

# четыре способа поставить одну задачу
.venv-demo/bin/python demo/record_reasoning_demo.py

# управление ответом: свободный ответ против управляемого
.venv-demo/bin/python demo/record_control_demo.py --key-file ~/.gigachat-key
```

Без ключа ролик можно снять на заглушке: добавьте `--fake`. Готовый файл
по умолчанию кладётся на рабочий стол.

Как это устроено: приложение запускается под псевдотерминалом фиксированного
размера, эмулятор терминала держит состояние экрана вместе с цветами, сценарий
«печатает» ввод с имитацией набора, а снятые кадры прореживаются в местах
ожидания — поэтому ролик укладывается в полминуты, не теряя ни одного этапа.
Ключ вводится скрытно и в кадр не попадает. Подробнее — в
[ARCHITECTURE.md](ARCHITECTURE.md).
