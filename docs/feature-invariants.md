# Инварианты и ограничения состояния

## Что добавлено

`AgentConfig.invariants` хранит правила, которые ассистент не вправе менять по
ходу разговора. Каждое правило имеет стабильный `id`, одну из четырёх категорий,
формулировку и необязательную причину:

- `architecture` — выбранная архитектура;
- `technical-decision` — принятое техническое решение;
- `stack` — ограничения по технологиям;
- `business-rule` — правило продукта.

Инварианты сериализуются вместе с конфигурацией, но не входят в
`Conversation.messages`, working memory, пересказ или картотеку фактов. Поэтому
служебные проверки не загрязняют историю, а обрезка и сжатие не могут удалить
ограничение.

## Управление в диалоге

Файл заранее готовить не обязательно. Агент распознаёт явную декларацию в
обычном сообщении:

```text
В проекте мы используем Kotlin и только. Java использовать нельзя.
```

Перед основным ответом отдельный анализатор возвращает структурированное
правило. Оно сохраняется в `AgentConfig.invariants`, после чего запрос и ответ
проходят обычные проверки уже с новым ограничением. В интерфейсе появляется
панель с сохранёнными `id`, а в `AgentResult` — поле `detected_invariants`.

Сначала дешёвый локальный фильтр ищет слова явной обязательности: `нельзя`,
`запрещено`, `обязательно`, `никогда` и английские аналоги. Слово `только`
срабатывает вместе с проектным контекстом вроде «используем», «стек» или
«система». Поэтому обычная реплика не создаёт дополнительного запроса. Если
маркер найден, модель отличает долгоживущее проектное правило от разовой
инструкции. Например, «ответь только кратко» не сохраняется.

Автораспознавание включено полем `invariants.auto_detect`; его можно отключить,
не отключая правила и ручные команды.

Команда `/invariant` показывает текущие
правила, а `add` добавляет или заменяет правило с заданным `id`:

```text
/invariant add stack stack.python Сервер только на Python | Командный стандарт
/invariant add бизнес business.no-negative Баланс не может быть отрицательным
```

Текст после `|` — необязательная причина. Категории можно писать по-русски:
`архитектура`, `решение`, `стек`, `бизнес`. Правки применяются к следующей
реплике, переживают `/new` и сохраняются в конфигурации сессии.

```text
/invariant remove stack.python
/invariant clear
```

## Как проходит запрос

```text
запрос пользователя
        │
        ▼
проверка запроса ── конфликт ──► объяснённый отказ
        │ совместим
        ▼
основной ответ с инвариантами в system prompt
        │
        ├─ вызов инструмента ──► проверка до исполнения
        │
        ▼
проверка ответа ─── нарушение ──► ответ скрыт, объяснённый отказ
        │ совместим
        ▼
ответ пользователю и запись в историю
```

Контролёр получает только перечень инвариантов и проверяемые данные. Он не
решает исходную задачу и возвращает короткий JSON. Ответ разбирает код:

- `allowed` обязан быть булевым;
- запрещающий вердикт обязан назвать хотя бы одно нарушение;
- разрешающий вердикт не может одновременно содержать нарушения;
- каждый `id` обязан существовать в доверенной конфигурации.

Если модель предлагает вызвать инструмент, контролёр проверяет имя и аргументы
до запуска обработчика. Конфликтующий вызов помечается как неуспешный и
возвращается модели с объяснением; внешний код при этом не выполняется.

Неразбираемый, противоречивый или ссылающийся на неизвестный `id` ответ
контролёра вызывает `InvariantCheckError`. Это закрытое поведение: без
надёжного вердикта потенциально нарушающий ответ наружу не выходит.

## Как объясняется отказ

Текст самого правила и его причина берутся из конфигурации, а не из ответа
контролёра. Контролёр добавляет только короткое описание конкретного конфликта.
Например:

```text
Не могу предложить это решение: оно нарушает заданные инварианты.
- `stack.python`: Серверная часть пишется на Python 3.12 с FastAPI
  Конфликт: запрос требует переписать сервер на Go
  Почему правило действует: это поддерживаемый командой серверный стек
Могу помочь подобрать вариант, который сохраняет эти ограничения.
```

`AgentResult` сохраняет `refused`, `invariant_checks` и
`invariant_violations`. Поэтому вызывающий отличает отказ политики от ошибки
провайдера и может показать точное правило без разбора естественного языка.

## Проверка

`tests/test_invariants.py` покрывает:

1. Сериализацию инвариантов отдельно от сообщений диалога.
2. Явное присутствие правил в системном контексте основного ответа.
3. Совместимый запрос и две успешные фазы проверки.
4. Конфликт запроса и отказ до основной генерации.
5. Нарушающий готовый ответ и его замену отказом.
6. Блокировку конфликтующего инструмента до вызова обработчика.
7. Закрытое поведение при неизвестном `id`.
8. Добавление, замену и удаление правила во время диалога.
9. Автоматическое распознавание декларации про Kotlin и последующий отказ Java.
10. Отсев разового указания «ответь только кратко».
11. Сохранение динамического правила до первого сообщения и после `/new`.
12. Проверку дубликатов и прежний одношаговый путь без инвариантов.

Готовый конфиг со всеми четырьмя категориями: `configs/invariants.yaml`.
