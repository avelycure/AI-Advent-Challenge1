# feature/response-control — управление ответом модели

Ветка отведена от `main` и перебазирована на него, поэтому сравнение ниже — это
разница именно с актуальной базой.

## Коротко

В `main` программа отправляет вопрос и показывает ответ таким, каким его вернула
модель. Форма ответа никак не задаётся и никак не проверяется: получится текст —
значит текст, получится список — значит список.

В этой ветке появился второй режим работы: **тот же самый вопрос отправляется
дважды** — свободно и с ограничениями, — а результаты сравниваются. Ограничения
задают формат, длину и условие завершения, а соблюдение формата не декларируется,
а проверяется разбором ответа.

## Что изменилось в поведении

| | Было (`main`) | Стало (эта ветка) |
|---|---|---|
| Форма ответа | какую вернёт модель | задаётся схемой: JSON, YAML или таблица Markdown |
| Длина ответа | ограничена только окном модели | `max_tokens`, ровно пять элементов, поле не длиннее 60 символов |
| Завершение | модель решает сама | стоп-последовательность в параметре `stop` и в инструкции |
| Проверка формата | нет | ответ разбирается и сверяется со схемой по каждому пункту |
| Что видит пользователь | один ответ | два ответа рядом, таблица сравнения и таблица проверок |

Измеримая разница на живом GigaChat, один и тот же вопрос:

| | Без ограничений | С ограничениями |
|---|---|---|
| Символов в ответе | 1412 | 347 |
| Токенов в ответе | 303 | 138 |
| Проверок пройдено | 2 из 6 | 6 из 6 |

Управляемый ответ короче на 54 процента и пригоден для машинной обработки без
разбора текста. Свободный не пригоден: его нельзя ни распарсить, ни предсказать.

## Что добавилось в коде

Новые файлы:

- `llmchat/controls.py` — форматы ответа, схема данных, построение инструкции
  и проверка результата;
- `compare.py` и `compare.sh` — инструмент сравнения;
- `demo/pipeline.py` — общий конвейер записи роликов, вынесенный из существующего
  рекордера, чтобы два рекордера не дублировали код;
- `demo/record_control_demo.py` — запись ролика про этот этап.

Изменённые файлы:

- `llmchat/client.py` — запрос научился принимать `stop` и `response_format`,
  ответ теперь несёт `finish_reason`, а непринятый провайдером параметр
  убирается и запрос повторяется;
- `llmchat/app.py` — шаг настройки принимает свой баннер, чтобы инструмент
  сравнения не показывал заголовок чата;
- `demo/record_demo.py` — переведён на общий конвейер;
- `requirements.txt` — добавлен `PyYAML` для разбора YAML.

Сам чат не изменился: его регрессия из 50 проверок по четырём провайдерам
проходит без правок.

## Почему контроль устроен из трёх слоёв

Ни одного слоя по отдельности не хватает, и это не теория — каждый вывод получен
живой проверкой.

**Инструкция** описывает структуру, даёт пример и запрещает всё лишнее. Самый
сильный рычаг: GigaChat оборачивает JSON в тройные кавычки даже при заданном
`response_format`, но перестаёт, если запретить прямо.

**Параметры запроса** — `max_tokens`, `stop`, `response_format` — работают на
стороне провайдера и не зависят от послушности модели. Но поддерживаются
неодинаково, поэтому клиент умеет убрать непринятый параметр и повторить запрос.

**Проверка результата** — единственное, что даёт право утверждать, что формат
соблюдён. Ответ разбирается и сверяется со схемой: число элементов, набор полей,
типы, длины строк, диапазон года.

## Что выяснилось про провайдеров

| Наблюдение | Провайдер |
|---|---|
| `response_format=json_object` даёт чистый JSON | YandexGPT |
| `response_format` принимается, но не мешает обрамлению | GigaChat |
| Явный запрет обрамления в инструкции работает | оба |
| Оборачивает YAML в тройные кавычки вопреки запрету | YandexGPT |
| Не обрывает генерацию по стоп-строке | GigaChat |

Последний пункт стоил отдельной отладки. GigaChat выдал маркер как `###\nКОНЕЦ###`,
разбив его переносом строки: провайдер не нашёл совпадения со стоп-строкой,
а очистка по точному совпадению тоже промахнулась — остаток ломал разбор JSON.
Теперь маркер снимается регулярным выражением с допуском на пробелы.

## Критичные и снимаемые нарушения

Проверки разделены на два вида, и это тоже следствие живой проверки, а не
изначальный замысел.

YandexGPT оборачивает YAML в тройные кавычки вопреки запрету. Я проверил три
средства — усиленную формулировку, отдельный запрет обратной кавычки, переспрос
с указанием ошибки — не помогло ни одно. При этом сами данные внутри безупречны.

Считать такой ответ непригодным было бы неверно, а молча скрывать отклонение —
нечестно. Поэтому **критичные** нарушения означают, что данные непригодны, а
**снимаемые** помечаются знаком `⚠`: обрамление снимается при разборе и на
результат не влияет.

Если управляемый ответ нарушил критичные проверки, программа один раз
переспрашивает модель с перечнем конкретных нарушений и сообщает в выводе, что
попытка потребовалась. Скрывать переспрос нельзя — это часть честного сравнения.

## Как проверить

```bash
./compare.sh                    # JSON, вопрос по умолчанию
./compare.sh --format yaml
./compare.sh --format md --prompt "Назови пять баз данных и год выхода"
./compare.sh --demo             # без обращения к сети
```

Проверено на матрице из шести комбинаций — два провайдера с живыми ключами
(GigaChat и YandexGPT) на трёх форматах. Во всех шести управляемый ответ даёт
пригодные данные; в одной комбинации (YandexGPT с YAML) остаётся снимаемое
замечание про обрамление, в одной (GigaChat с Markdown) однажды потребовался
переспрос.
